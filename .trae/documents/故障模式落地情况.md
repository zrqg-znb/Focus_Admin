# 故障模式产品级落地状态与工作流录入方案

## Summary
- 落地状态改为三层语义分离：`全局绑定关系` 继续描述故障模式和资源库的资产关系，`产品级落地` 负责描述某个 `产品 + 子系统` 下是否真的落地，`任务态草稿` 负责承接工作流中尚未生效的编辑结果。
- 落地范围固定为 `产品 + 子系统`，覆盖 `故障模式本身 + 产线拦截策略 + 故障处理措施 + 维测手段 + 华佗诊断方案`，本期不扩到测试用例。
- 任务侧交互固定为 `独立 LandingConfigDrawer`；`CREATE / REVISE` 在 `PROCESSING` 时都可维护落地状态，且提交评审前必须把当前工作集里每条故障模式及其当前绑定资源的落地状态全部补齐。
- 产品统计页切到“显式落地”口径；现有三态图表继续保留，但改为基于显式落地推导，而不是再用“有无全局关联”做间接推断。
- 存量基线迁移采用“按当前关联先回填为已落地”的兼容策略，避免上线后产品看板整体失真。

## Key Changes
### 1. 绑定关系与数据模型
- 保留现有全局关系表不变：`FailureModeInterceptionStrategyRel / FailureModeHandlingMeasureRel / FailureModeObservationMethodRel / FailureModeHuatuoDiagnosisRel` 仍只表达“全局资产绑定”，不增加 `is_landed`。
- 将 `ProductFailureMode` 升级为产品级主锚点，新增 `is_landed: bool`，用于记录该故障模式在当前 `产品 + 子系统` 下是否已落地。
- 新增 4 张产品级落地表，并统一挂在 `ProductFailureMode` 之下：
  - `ProductFailureModeInterceptionLanding(product_failure_mode, interception_strategy, is_landed)`
  - `ProductFailureModeHandlingLanding(product_failure_mode, handling_measure, is_landed)`
  - `ProductFailureModeObservationLanding(product_failure_mode, observation_method, is_landed)`
  - `ProductFailureModeHuatuoLanding(product_failure_mode, huatuo_diagnosis, is_landed)`
- 以上 4 张表都只存当前生效基线结果，唯一键固定为 `product_failure_mode + resource_id`，并对 `product_failure_mode`、`resource_id` 建索引；同一资源即使在不同产品或不同故障模式中出现，也分别独立记录。
- 任务态不直接写产品基线，推荐在 `TaskFailureMode` 上新增 `landing_payload_json`，作为任务内工作副本；其结构固定包含：
  - `failure_mode_is_landed: true | false | null`
  - `interception_rows / handling_rows / observation_rows / huatuo_rows`
  - 每行至少包含 `resource_id / label / group_key / is_landed: true | false | null`
- `null` 只允许存在于任务草稿层，表示“尚未填写”；真正写回产品基线时只能落成显式 `true / false`。

### 2. 工作流与任务工作台
- `CREATE / REVISE` 的工作台行级操作新增 `落地配置`，打开独立 `LandingConfigDrawer`；`DELETE` 不开放编辑，只在需要时展示只读摘要。
- `LandingConfigDrawer` 只负责产品级落地，不复用 `FailureModeDrawer`；内容固定为：
  - 顶部：当前故障模式、产品、子系统、任务类型、任务状态
  - 第一块：故障模式本身“已落地 / 未落地”
  - 后续四块：按当前故障模式“当前生效或当前任务草稿中的绑定关系”展示资源清单，并逐行选择“已落地 / 未落地”
- `CREATE` 任务中，只要某条故障模式进入任务工作集，不管是“绑定已有”还是“快速新增”，都要补录该条的产品级落地状态。
- `REVISE` 任务初始化时，除了预装当前基线故障模式，还要把当前 `ProductFailureMode + 4 张产品级落地表` 的结果一起预装进 `landing_payload_json`。
- 当 `REVISE` 任务里修改了故障模式草稿导致绑定资源集合变化时，落地草稿要自动归一：
  - 仍存在的资源保留原落地值
  - 新增资源自动补进列表，初始 `is_landed = null`
  - 被移除的资源从任务落地草稿中剔除
- 提交评审前增加强校验：
  - 每条任务工作集故障模式都必须有 `failure_mode_is_landed != null`
  - 每个当前绑定资源都必须有 `is_landed != null`
  - 任一条未补齐则 `POST /submit` 返回 422，并带回未完成故障模式列表
- 关闭任务时的落地同步顺序固定为：
  - `CREATE`：先落 `ProductFailureMode`，再写 4 张产品级落地表
  - `REVISE`：先应用故障模式主数据草稿，再按最终关系集同步基线，最后重写产品级落地表并删除失效资源行
  - `DELETE`：删除 `ProductFailureMode` 时级联删除对应 4 张产品级落地表
- 任务日志新增 `save_landing` 动作，记录谁在何时保存了落地配置。

### 3. 统计口径与可视化
- 产品统计页全面切到显式落地语义，统计源固定为当前筛选范围内的 `ProductFailureMode + 4 张产品级落地表`，不再用“是否存在全局绑定关系”直接代替落地。
- 产品统计页新增一组“故障模式本身落地”指标：
  - `baseline_failure_mode_count`
  - `landed_failure_mode_count`
  - `pending_failure_mode_count`
  - `pending_rate`
- 产品统计页新增 `故障模式落地情况` 图表，固定展示 `已落地 / 未落地` 两态。
- 现有四类能力图表继续保持三态，但改为如下推导规则：
  - `不涉及`：该能力在当前故障模式上不是必配
  - `已落地`：该能力是必配，且该能力下当前所有绑定资源都显式标记为 `is_landed = true`
  - `待开展`：该能力是必配，但当前没有绑定资源，或当前有任一绑定资源为 `false`
- “全部都已落地才算已落地”的规则统一适用于：
  - 产线拦截策略：当前绑定的全部拦截策略都为 `true`
  - 华佗诊断：当前绑定的全部华佗方案都为 `true`
  - 故障处理措施：按 `检测 / 预防 / 自愈` 分组，每组内全部绑定措施都为 `true`
  - 维测手段：按 `流水日志 / DMD 点位 / FMP 点位` 分组，每组内全部绑定手段都为 `true`
- `pending_failure_mode_count` 的口径固定为：故障模式本身 `is_landed = false`，或任一必配能力未达到“全部已落地”。
- 产品统计页的子系统表改为落地导向字段，不再继续使用“原始关联数量”作为主展示，固定保留：
  - `子系统`
  - `基线故障模式数`
  - `已落地故障模式数`
  - `待开展故障数`
  - `待开展率`
  - `状态灯`
- 多产品、多子系统聚合继续沿用现有页面选择逻辑；统计对象改为所选 `ProductFailureMode` 的并集。
- 现有主数据关系洞察 Drawer 的 `landed_product_count` 语义同步切到显式落地：
  - 故障模式洞察按 `ProductFailureMode.is_landed = true` 统计唯一产品数
  - 各资源洞察按对应产品级落地表中 `is_landed = true` 统计唯一产品数

### 4. Public APIs / Types
- 新增任务侧落地接口：
  - `GET /api/failure-mode/workflow/tasks/{task_id}/failure-modes/{failure_mode_id}/landing`
  - `PUT /api/failure-mode/workflow/tasks/{task_id}/failure-modes/{failure_mode_id}/landing`
- 新增类型：
  - `TaskFailureModeLandingOutSchema`
  - `TaskFailureModeLandingSaveSchema`
  - `TaskFailureModeLandingRowSchema`
- `TaskFailureModeLandingOutSchema` 至少返回：
  - `task_id`
  - `failure_mode_id`
  - `failure_mode_brief`
  - `failure_mode_is_landed`
  - `landing_completed`
  - `interception_rows`
  - `handling_rows`
  - `observation_rows`
  - `huatuo_rows`
- `GET /api/failure-mode/workflow/tasks/{id}/failure-modes` 追加任务列表摘要字段：
  - `landing_completed: bool`
  - `failure_mode_is_landed: bool | null`
  - `landing_resource_total: int`
  - `landing_resource_landed_count: int`
- `POST /api/failure-mode/workflow/tasks/{id}/submit` 增加落地完整性校验；若未补齐，返回明确的未完成故障模式列表。
- `FailureModeProductStatisticsOverviewItem` 增加：
  - `landed_failure_mode_count`
- `FailureModeProductStatisticsSummary` 增加：
  - `failure_mode_landing_status`
- `FailureModeProductStatisticsSubsystemRow` 改为产品落地导向字段，不再沿用全局统计的原始 relation_count 结构。
- 新增 4 组产品级落地模型对应的序列化与 service helper，但不新增单独页面 CRUD；维护入口只在任务工作台。
- 数据迁移增加一次性 backfill：
  - 对现有 `ProductFailureMode` 统一写入 `is_landed = true`
  - 按当前全局绑定关系为 4 张产品级落地表初始化 `is_landed = true`
  - 已被历史覆盖的真实落地差异不追溯，由后续修订任务纠正

## Test Plan
- `CREATE` 任务中绑定已有故障模式后，工作台能打开 `LandingConfigDrawer`，初始为未填写状态，提交评审前必须补齐。
- `CREATE` 任务中快速新增故障模式后，既能继续编辑主数据，也能单独维护该条的产品级落地状态。
- `REVISE` 任务创建后，已有基线故障模式的落地状态能正确回显到任务草稿。
- `REVISE` 任务里新增或移除绑定资源后，落地草稿能自动补齐新增项并清理被移除项。
- `DELETE` 任务不出现落地编辑入口，关闭后会级联删除产品级落地记录。
- 同一能力下绑定多条资源时，只有“全部资源都已落地”才会在产品统计里显示为 `已落地`。
- 产品统计页在“全部平台项目 / 单产品 / 多产品 + 多子系统”三种视角下都能正确聚合显式落地结果。
- 产品统计页的新 `故障模式落地情况` 图表、原有能力图表、子系统表的待开展数和待开展率都与同一套显式落地数据一致。
- 关系洞察 Drawer 的 `landed_product_count` 与产品统计页口径一致，不再出现“看板未落地但洞察里已算落地”的冲突。
- 存量数据迁移后，原有产品基线不会全部变成未落地；后续修订任务可以继续纠正个别产品的真实状态。
- 回归验证：现有 `FailureModeDrawer` 主数据编辑、任务修订草稿、产品基线同步、产品统计筛选、多产品选择逻辑不回退。

## Assumptions
- 最终生效层只存二值 `true / false`；“未填写”只存在于任务草稿层，用 `null` 表示。
- 故障模式本身的落地状态与四类资源落地状态允许独立记录，不做强制联动；产品统计里的“待开展”按统一聚合规则推导。
- 本期不新增独立“产品落地配置页”，唯一正式维护入口就是任务详情页工作台里的 `LandingConfigDrawer`。
- 全局主数据页上的直接编辑不会自动重算已落地产品的产品级落地结果；产品级落地的正式生效仍以工作流任务关闭为准。
- 全局统计页继续保留“配置/关联”视角，不在本期同步改造成产品落地视角；“显式落地”只在产品统计页、任务工作台和洞察计数中落地。
